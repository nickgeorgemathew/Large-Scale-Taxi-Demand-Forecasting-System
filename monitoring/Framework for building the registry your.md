What data does a registry entry need beyond just a filename? Just "production_model": "lgbm_v3.pkl" tells you what's live but nothing about why — when was it promoted, what were its validation metrics at promotion time, who/what promoted it (manual vs auto-retrain)? Single-level rollback (previous_model) vs full history? The AI version only keeps one step back. Think about it: if you promote v4, discover it's bad, roll back to v3, then v3 also turns out to have issues — can you get to v2? With only a previous_model pointer, no. Is a full history: [v1, v2, v3, v4] list with a current_index a meaningfully better design, and what's the extra complexity cost?
Concurrency — same question as PredictionLogger's read-modify-write race condition from earlier. If your monitoring loop calls rollback() at the same moment your training pipeline calls promote(), what breaks? Do you need this to be safe for this project, or is that over-engineering for a single-process portfolio demo? Be honest about which.
What happens on rollback() if there's nothing to roll back to? — the AI version just logs a warning and silently no-ops. Is silent no-op the right behavior, or should the caller (your AlertManager.trigger_action) know it failed so it can escalate instead of assuming a rollback succeeded when it didn't?

Don't write code yet. Answer these design questions first, on paper or in a comment block, the same way you'd be expected to reason out loud in a system-design interview:

What's your data structure for history? A flat list ["v1", "v2", "v3"] with a current_index integer? Or a list of dicts, each with {"version": "v3", "path": "...", "promoted_at": timestamp, "metrics_at_promotion": {...}}? Given what you said about wanting to debug bad promotions later — which structure actually lets you answer "why did we promote v3, what did it look like at the time"?
Rollback semantics — if history is [v1, v2, v3, v4] and current_index=3 (pointing at v4), and you call rollback(), what should current_index become? Now — critical question — if you then promote a new v5, what happens to v4? Does it disappear from history, or does it stay, with v5 appended after it? Think about what a real ML team would want: do you ever want to "redo" back to v4 after having gone to v5, or is going forward from a rollback point supposed to overwrite the abandoned branch? (This is genuinely the same conceptual problem as git branching/history — useful to notice that parallel.)
What triggers a promotion? Right now promote() is presumably called manually or by your retrain pipeline finishing. Should a newly retrained model become current automatically, or should it require passing some validation check first (e.g., new model's val metrics beat current model's) before promote() is even called? Where does that gate belong — inside ModelRegistry, or in the calling code (ModelopsPipeline) that decides whether to call promote() at all? Separation of concerns question — which class should own that decision?
What does get_active_model_path() need to guarantee? If current_index points at a version whose .pkl file has been deleted from disk (manual cleanup gone wrong, disk space pruning, whatever) — should get_active_model_path() silently return a path to a nonexistent file, or should it validate the file exists and raise/log clearly? What's the failure mode you want your serving API to hit — a confusing downstream FileNotFoundError from joblib, or a clear error from the registry itself?
